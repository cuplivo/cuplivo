输入消息与AI聊天

子会话标题栏：不动

你说得对，这里有东西：手机端是 头像 + 标题（16px）+ 第二行「模型 (provider)」（home_mobile_layout.dart:200-243），右侧还有小地图与新建两个动作（:278-314）。第二行已经是模型，塞不进「来自父对话」。

所以：标题栏一个字都不改，子会话就是普通会话。它是子代理这件事，由侧边栏那一行的小标签和面板承担；「查看父对话」放在面板的长按菜单里。

如果你要更强的信号，最小改动是在标题前加一个 12px 的 子代理 徽标（Row 包住 AnimatedTextSwap），第二行不动。我倾向先不加——从侧边栏点进来的那一行本身就带着标签。

要不要现在就把「指定助手」和「绘图」做成目标

你说得都对，但它们是两件事，而且方向相反：指定助手是给「派给谁」加一类答案；吸收绘图是把「派出去做什么」的第二种产物并进来。我先把它们拆开说。

指定助手
动机成立：默认派给「本助手的分身」，零配置；有需要时指名某个专长的助手。这与 v3 的差别是实质的——v3 必须选目标，现在是特例才选。但有一条线不能动：工作区永远继承调用方。一旦按目标助手解析，本轮要修的根因原样回来。目标只能贡献 模型 / 系统提示 / 工具集。
风险
助手编辑页多一栏（开关 + 「被委派时我是谁」的描述）。描述写不好就会重演 v3 的「该开的都开了，却什么都不发生」——那时候的失败多半不是模型不行，是没人知道该填什么。
吸收绘图
该吸的是基建，不是工具。两者共有的只有：id 即幂等键、终态写回、取消、状态到卡的映射——这四样本来就该抽成一套 job 引擎。但结果落点完全不同：图的落点是「正文里的一个位置」（![]() 原地替换成图），子代理的落点是「一条消息 + 一个会话」。
为什么工具别合
合成 delegate(kind:'image') 的代价：给一张图假造一个会话（它没有会话）、每次画图先让模型选 kind、然后把「占位符替换 / 比例 / asset」这些特例照样一个不少地特判回去。省下的是一个 generate_image 注册，换来一个判别字段和一具空会话。
能合的
配置面可以合：一个「能力」入口里并列 子代理 / 绘图，各有自己的开关与模型。用户看到的是一个地方，模型看到的是两个契约。
我的结论
v1 只做通用子代理；把 job 基建抽出来（顺带把生图迁到它上面，反正还没发版）；「可被委派的助手」作为紧接的第二片，规则写死「工作区继承调用方」；绘图保持独立工具，只在配置面并排。

如果选「现在就一起纳入」，形态是这样的

  • delegate(task, label, assistant?)：不给 assistant → 通用子代理（继承本助手）；给了 → 那个助手，但工作区仍继承调用方。
  • 助手编辑页新增一栏：可被委派（开关）+ 被委派时的描述（一句话，写它能干什么，不是它是谁）。默认关。
  • 工具描述里枚举「当前可指名的助手」——这串名单进每个请求的 system prompt，会话变得听话也变得更长。
  • 面板与侧边栏要显示每条子代理的目标助手；「通用」与「指定」的徽标要能分辨。
  • 绘图若也做目标：delegate(kind:'image')，仍要特判占位符替换、比例、asset。

你提的 await：下一轮专门谈，先把问题摆清楚

「模型等子代理、自己没事干」有三种读法，选错了会同时得罪两头（干等的浪费 vs 停下的偷懒感）：

  • 直接停下：模型不调任何工具就结束这一轮。用户看到「已经派了，等它回来」——它必须这么说，工具描述里要写死。零新机制，但模型经常意识不到该停。
  • await 工具：多一个 await_subagent(id)，阻塞到结果或超时。语义清楚，但它把 wait-only 那套又请回来一半，还要回答「超时了算什么」。
  • 结果回灌：派出去后不再给模型选择，子代理结束 → 结果作为 tool result 回到本回合。那等于 wait-only，只是发生在服务端。

这一条和 UI 相关（条上要不要显示「在等它」、模型停下时那条分隔线什么时候出现），所以我把它放到下一轮，和「模型停下时用户看到什么」一起画。

这一版定下的

  • 条：静止文字 + 括号里时长，照生图卡头的写法；不再用扫光。
  • 面板：按 createdAt 倒序、每行 duration、四种状态、语义靠图标、颜色只区分「要不要你动手」。
  • 子会话标题栏一个字不改；「来自父对话」在面板里。
  • 「子代理完成」与「用户同时说话」不做抢占规则——很少见。

必须接受的代价

  • 只有通用子代理时，派不了「那个专门写 SQL 的助手」。v1 的所有子代理都是当前助手的分身：同模型、同提示、同工具。
  • 「可被委派」这个概念要等到第二片才存在。届时助手编辑页会多一栏，那是一次真正的范围扩张，不是补丁。
  • 绘图与子代理在工具层永远是两个。模型要学两个调用，配置面只是把它们摆在一起。
  • job 基建抽出来会动到已合入的生图。虽然还没发版，但它有 18 条测试与一套卡；迁移本身是一笔要还的债。

这一轮只定一件事：v1 只做通用子代理（推荐），还是现在就同时纳入「可被委派的助手」与「绘图作为目标」。定了之后：先出核心逻辑伪代码（数据流 / 不变量 / 失败模式），再谈 await 与「模型停下的那一刻用户看到什么」。
