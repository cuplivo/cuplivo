# 第 3 轮·A｜保留「自动切换话题」，让它在两种桌面布局里都真的生效

> 这条设置今天只出现在桌面显示设置里（`_ToggleRowAutoSwitchTopicsDesktop`），默认**关**。
> 它的问题不是"要不要切视图"，而是它在右侧布局里**显示着却永远不生效**（F5）。

## 1. 现状（三格只有一格是真的）

| 布局 | 设置开 | 设置关 |
| --- | --- | --- |
| 桌面·话题在左 | 点**助手**：侧栏切到话题 tab ✅ | 不切 ✅ |
| 桌面·话题在左 | 点**群**：不切 ❌（同一个判断只写在助手分支里） | 不切 ✅ |
| 桌面·话题在右 | 什么都不发生 ❌（`useDesktopTabs` 为假，整段判断被跳过） | 不切 ✅ |
| 移动 | 设置不出现；点 owner 关抽屉 | 同左 |

所以「自动切换话题」现在表达的是「在左侧布局里、并且点的是助手的时候，切一下」。
I5 说：要么不出现，要么出现时真的生效。

## 2. 改完之后

| 布局 | 设置开 | 设置关 |
| --- | --- | --- |
| 桌面·话题在左 | 点助手 / 点群都切到话题 tab（侧栏收着就先展开） | 不动 |
| 桌面·话题在右 | 点助手 / 点群都打开右侧面板并停在「话题」页 | 不动 |
| 移动 | 设置不出现；点 owner 关抽屉（不变） | 同左 |

实现就是第 2 轮 2.3 的 `revealTopics()` 一个函数，三个调用者共用：
头像点击（`_revealAssistantTopics` 已有）、热键（`ChatAction.toggleLeftPanelTopics` 已有）、
owner 点击（本轮新增）。设置只在它里面被读一次。

## 3. 为什么保留这个设置而不是删掉

- **默认是关的。** 删掉它等于「一律切视图」，会让多数用户的行为变掉，
  与目标书 §4 的横切验收「开关关闭时行为与今天逐格相同」正面冲突。
- 它现在表达的东西是真的：有人不希望点一下 owner 就把侧栏切走（尤其在右布局，
  切视图还会占用聊天区宽度）。
- 保留它，也让「右布局也生效」这件事是**用户可选**的，而不是强加的布局变化。

## 4. 代价与风险

- 右布局下打开面板会占宽度、聊天区变窄。这是设置的语义本身，可以用它关掉；
  但**第一次**遇到的人会看到布局跳一下。验收里那一格要按真机确认观感
  （面板以 docked 还是 overlay 呈现，取决于窗口宽度阈值 849）。
- 设置行不加解释文字（UI 成本规则）。它是开关，标题「自动切换话题」在两种布局下都成立。
- 移动端保持不出现：这个设置没有移动端等价物（抽屉里没有 tab），出现即违反 I5。

## 5. 被否掉的方向（写在这里，免得下一轮重新讨论）

- **右侧布局隐藏这个设置。** I5 字面能满足（不出现就不必生效），但 F5 里的
  「点助手/点群不切视图」会变成"永远不切"，与目标书 §4 矩阵「可见视图：按设置显示话题页」
  直接矛盾——右侧布局就没有设置可依。
- **删掉设置。** 见 §3，与横切验收冲突，且要动 13 个语言的 ARB 与 settings 搜索索引。

## 6. 本轮要确认的

保留这个设置、并让它在两侧布局都生效，是否就是 §6-B 里「I5 只在其能生效的地方生效」的读法。
