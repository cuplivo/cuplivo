深层委派：两个工具，方向写在名字里

向上和向下是两个名字：reply_to_delegator 只回委派方，send_message 永远发给自己的某个孩子。没有可选参数，也不会猜错方向。

这个子代理看到的委派工具

工具用途参数
delegate再派一层（受 levels 限制）task, label（+ target）
await_job等某个孩子结束job_id
reply_to_delegator向上回委派方text
send_message向下发给自己的孩子job_id, text
interrupt叫停自己的孩子job_id

schema

深度 2 的子代理：向上

每个有委派方的对话都有
{
  "name": "reply_to_delegator",
  "required": ["text"],
  "properties": {
    "text": { // 说什么 }
  }
}

深度 2 的子代理：向下

只有还能委派的人有
{
  "name": "send_message",
  "required": ["job_id", "text"],
  "properties": {
    "job_id": { // 哪个孩子 },
    "text":   { // 说什么 }
  }
}

两种调用

向上：回委派方

reply_to_delegator({ "text": "读到第 3 层了，缺 config" })

和今天子代理的 send_message 是同一件事，只是换了名字。

向下：给自己的孩子

send_message({
  "job_id": "c-42",
  "text":   "改用 YAML"
})

和根对话的 send_message 完全一样，同一个 schema。

一轮的样子

深度 2 子代理delegate → 拿到 job_id: c-42，继续干活
c-42reply_to_delegator → 深度 2 子的对话里出现「子代理消息」
深度 2 子代理send_message({job_id: c-42, text}) → c-42 里出现「委派方消息」
深度 2 子代理interrupt({job_id: c-42}) → c-42 停下；不写结果行

代价：现有子代理的 send_message 要改名成 reply_to_delegator——简报文案、工具卡标题、测试与历史里的工具调用名都跟着动；子代理的工具数从 1 个消息工具变成 2 个。
