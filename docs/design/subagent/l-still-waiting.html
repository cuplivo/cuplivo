让那张卡一直转到子代理结束

异步之后最难受的一格：模型说完「派了」就停了，工具卡照常一秒钟变完成——用户扫一眼，以为活干完了，人走了。所以让卡的状态跟着子代理活，而不是跟着 tool call 返回。

停下的那一刻

卡不响。tool call 早就返回了 started，但这一格显示的仍然是「运行中 (13.3s)」——因为它跟的是子代理的生命周期，不是那次调用。生图的卡就是这么做的：ImageJobCard 的显示由 coordinator 的活 job 决定，而消息里的 part 只是一张快照（chat_message_widget.dart:3192-3226）。

两处同步，不是两处状态。条和卡都读同一个 registry 条目；卡是「在这条回复里」，条是「在这个会话里」，数据只有一份。

模型被要求停下。工具描述里写死：派出去之后不要编造结果、不要重复派人，没有别的事可做就直接结束这一轮（你上一轮提的那条）。它停不停是它的事，但停下时界面上不会装成「已完成」。

结束的那一刻

卡变勾 + 时长定住，分隔线出现，条消失。三件事同一次写入，因为它们读的是同一个终态。

重启：进程被杀时卡停在「运行中」——渲染层派生「已中断」，不落库、不自动重跑（生图那套读法，image_job 的教训）。

不唤醒：分隔线之后没有自动的下一句；用户想继续，就自己说一句——这正是你上一轮定的。

如果选「卡照常立刻完成」，就是这个样子

回复写完时卡已经是一行勾，时间线上没有任何「还在跑」的痕迹；只有输入框上方那条在动。用户不盯着输入框就会以为结束了——这正是你提的那个「以为干完、一看没有、觉得模型偷懒」。

你问的「查看主对话」横条：容易，而且有现成的形

  • 形就是 ContextOperationDivider（28px、两侧 1px 线、中间 12.5px 字 + 图标 + chevron，context_node_divider.dart:129-165），和「清空上下文」那条一模一样。
  • 位置：子会话消息列表的末尾一条 + 开头一条。它不需要进消息表——列表本来就支持在消息之间插非消息项（message_list_view.dart:2212-2225 在渲染上下文操作分隔线）。
  • 判据：只有带 subagent.parent 的会话才画这两条；普通会话一个字都不多。
  • 成本：一个 footer 项 + 一个 header 项，视觉零新增。要留意的只有虚拟列表的 index 换算（它已在处理上下文分隔线，同一套）。

你让我预留的空间

  • extras 里留 subagent.target：v1 永远写 general；第二片再写助手 id 或 image。不占列、不改 schema。
  • 面板行模型留 target 字段，v1 不显示——这样第二片的「这个子代理派给了谁」不是改模型，是加一列 UI。
  • 工具参数不加 assistant?：加了没人填、模型也不会填，就变成 v3 那种「开了却什么都不发生」。预留要留在数据里，不是留在契约里。

await：合并，但合并的理由是 job，不是对称

同意一个 await_job(job_id)。它站得住的理由不是「两个工具长得像」，而是两者会共用一套 job 引擎：同一个 id 空间、同一套终态（completed / failed / interrupted）、同一套超时。既然如此，等的东西是 job，不是"图"或"子代理"。

  • 返回：终态 + 产物。图 → asset uri；子代理 → 它的最终文本 + conversation_id。同一层，两种 payload。
  • 超时：给一个上限（生图那边是 300s），超时返回 still_running 而不是失败——"慢"和"坏"是两件事。
  • 描述里写死：await_job 是你选择等时才用的，默认路径不需要它；等的时候不要同时调别的工具。
  • 它不改变上面那条「卡跟着子代理活」：await 是模型的选择，卡是用户的观感，两者独立。

这一版定下的

  • 工具卡的运行态跟着子代理，不跟着 tool call；卡与条读同一个 registry 条目。
  • 结束那一刻三件事一起发生：卡变勾、分隔线出现、条消失。
  • 子会话首尾各一条「查看主对话」的横条，形与「清空上下文」相同。
  • 预留 subagent.target 与面板行的 target 字段；工具参数不加。
  • await_job(id) 一个工具服务两种 job，超时返回 still_running。

必须接受的代价

  • 一张转很久的卡本身也是一种谎：它写着「运行中」，可那次工具调用其实早就结束了。语义上要接受「这个卡代表委托，不代表这次调用」。
  • 两处显示同一个状态（卡 + 条），总会有人怀疑它们会不会不同步；只能靠"读同一个条目"这一条纪律。
  • 模型不按描述停下时，这条设计救不了——卡转着，它却继续干别的，界面反而更难看懂。
  • 首尾两条横条在很短的子会话里会挨得很近，看着像两条分隔线夹着一句话。

这一轮只定一件事：模型停下、子代理还在跑的时候，那张工具卡是继续显示「运行中」直到子代理结束（推荐），还是照常立刻变勾、把状态只留在输入框上方那条。定了之后就进核心逻辑伪代码：数据流、不变量、失败模式。
