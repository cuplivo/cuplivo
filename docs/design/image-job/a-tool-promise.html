这一版定下的

  • 图不是工具卡：它是消息里的图片块。显示工具卡片关掉时插图照样显示 —— 图是内容，不是工具日志。
  • 工具返回承诺：uri 已分配、字节未写；part 由工具结果创建，不从正文里解析路径，「这条路径是承诺的吗」有结构性的答案。
  • 约定已存在：![alt](generated) 今天就被认作占位（_ImageLineKind.placeholder），只是被吞掉、什么都不显示；本轮把它渲染成图片块并绑上 job。
  • 刷新靠 part：ImagePart.unavailable 已存在且持久化；字节落盘后 part 更新，骨架自动换成图。
  • 提示词不在卡片上：复制、编辑重生成、取消、模型、用量都在 ⋯ 面板里。
  • 不需要 workspace：图走现有 asset 存储，和粘贴图、宿主生图的图同一条路。

必须接受的代价

  • 每次生图多一次模型续写：工具结果要回灌，上下文重发一遍。
  • 图片块要在 timeline 里与工具 part 分开渲染，还要绕开「显示工具卡片」和导出里的工具卡裁剪 —— 一处新分支。
  • 占位状态要进 parts，否则重启后分不清「还在画」和「已中断」。
  • 工具参数每加一个（比例、质量、参考图），schema 长一截，模型选错的面积也大一分。

分水岭

A 的信任来自结构：part 由工具结果造出来。代价是那次续写。
B 的信任来自语法：part 由正文解析出来。省掉续写，换一层文本协议。

两个方案共用：图片块与 (6.0s) 状态行、⋯ 面板、job 状态机（queued → running → completed / failed / cancelled / interrupted）、重启中断、schema 5、先接一个后端。统计只记卡片这一行的用量，不接统计页：kelivo#1492 要新增 usage_events 账本表，那是 schema 6 的事。Gemini Image 这类走 chat 接口、返回 markdown 链接的，是宿主的另一条路：渲染层已有 markdown 图片与独立图片行识别，不进 job，第一版不动。
