发消息…

模型拿到什么：{status:"awaiting_user", proposal_id}，这一轮到此为止 —— 它拿不到图，也不必等图。

用户按什么：「生成插图」→ job 从 queued 开始，之后与 A 走同一套状态机；「这次不要」→ declined，不花钱、不留 job。

批准之后：同一张卡变成占位、再换成图；失败/取消可重试，和 A 完全一样。

一条硬规矩：正文不许承诺「图在下面」—— 图是否存在，不由模型决定。

这一版定下的

  • 工具是proposal而不是 generation：模型只提议，批准才提交 job。
  • 提案卡带 prompt 原文和比例，用户在花钱前看得见、改得了（改 prompt 或直接拒绝）。
  • 批准后复用同一套 job 生命周期与占位卡；拒绝是终态，不重试。
  • 「配图」是显式动作，不是默认行为；模型不把图写进自己的叙述。

必须接受的代价

  • 每张图多一次点击；配图从默认行为变成需要确认的操作。
  • 模型这一轮拿不到结果，回复的完成度和图脱钩；要它评论这张图，得再来一轮。
  • 用户不点，回复里就没有图；正文若承诺了图，就落空 —— 靠「不许承诺」的提示词规矩兜。
  • 工具契约多一个 awaiting_user 状态、一套提案/拒绝态 UI，是在 job 机制之外再加一层。

分水岭

B 是用户按下「开始画」。好处是花钱前能看一眼 prompt；代价是「配图」永远需要一次确认。

两个方案共用的部分：job 生命周期（queued → running → completed / failed / cancelled / interrupted）、原位置换、失败与取消可重试、重启中断、schema 5、先接一个后端。还没定的：工具命名与 await_image 的具体形态、默认后端、图像模型放全局还是按助手、占位卡的具体视觉、VLM 检查、context injection —— 都排在这一轮之后。
