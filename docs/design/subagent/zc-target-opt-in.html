子代理 · 第二片 · 委派目标为助手 · 方案 B

只有标了「可被委派」并写了一句介绍的助手才能被指名

同一个 delegate(task, label, assistant?)，同一条工作区规则（永远来自调用方）。变的只有名单从哪来：不是「所有助手」，而是开了开关、写了一句话的助手。助手编辑页的「子代理」弹窗因此多出第二组。

多出来的一组：开关 + 一句话

可被委派默认关。关着的助手不进任何人的名单，对模型不存在。

那一句话是模型选人时唯一读到的东西，所以它必须写「把需求写成 SQL 并解释执行计划」这种，不是「我是一个数据库专家」。空着就回落到名字——等于方案 A 里的一条。

放哪：「子代理」弹窗分两组，派出去 / 接进来。一个入口，两件事，不另开页面。

契约：名单短，每行带介绍

{ "name": "delegate",
  "parameters": {
    "task": "…", "label": "…",
    "assistant": {
      "type": "string",
      "enum": ["SQL 专家", "翻译官"],
      "description": "Omit to run the task as yourself. Available assistants:
                      SQL 专家 — 把需求写成 SQL 并解释执行计划
                      翻译官 — 中英互译，保留术语与格式
                      Name one to run it as them: their prompt, model and tools." } },
  "required": ["task", "label"] }
// 没有任何助手开了「可被委派」→ 整个参数不出现，和今天一模一样。
  • 数据：Assistant JSON 加两个字段 subagentTargetEnabled / subagentTargetDescription，schema 仍是 5。子会话 extras 同 A：subagent.target = 'assistant' + subagent.assistant_id。
  • 谁贡献什么：与 A 完全一致——目标出提示 / 模型 / 工具；调用方出工作区 / 授权 / 深度；模型优先级先调用方覆盖、再目标自己的。
  • 失败模式：A 的全部，外加一条：开了开关但介绍空着 → 回落到名字，不拒绝。
  • 界面：工具卡与面板同 A，多出的只有上面这一组设置。

好处

  • 名单短而准。模型读到的是为委派写的一句话，不是名字；选错的概率比 A 低。
  • 用户决定哪些助手暴露给模型。40 个助手的用户只标 3 个，每个请求多 3 行，不是 40 个名字。
  • 令牌成本由用户控制，不需要以后再补一个来源侧筛选。

代价

  • 这正是 v3 的形状。目标要 discoverable + 介绍，来源要开局部工具——「该开的都开了，却什么都不发生」。v1 放弃它就是为了这条。
  • 每个想被指名的助手要配两样。那一句话没人知道怎么写；写不好模型就选错——比名字选错更糟，因为用户以为自己配好了。
  • 功能默认不可见。要两个以上助手各配一遍，模型才有名单。没配的用户看到的和今天一样，却多了一个开关。
  • 助手编辑页多一组控件，是一次真正的配置面扩张。

这一轮只定一件事：谁能被指名——任何助手（方案 A），还是只有标了「可被委派」并写了一句介绍的助手（本方案）。
