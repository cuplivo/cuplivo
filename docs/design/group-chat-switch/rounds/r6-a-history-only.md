# 第 6 轮·A｜只补历史，本轮不把自己登记成 unit

> §7 的三处对齐照做；但「本轮的改动如何进入下一次 rebase」留给下一次整理 pass 决定。

## 1. 要落的四件事

1. **`CHANGELOG.md` / `CHANGELOG_CN.md`**：下一版（`4.8.0` 或 `4.7.1`）的 `Fixed` 新增一条，
   用用户语言写清三件已修的事（群话题点助手会离开群、群卡片点开侧栏跟着切、话题在右也生效），
   引用 #1092。
2. **4.6.0 条目加一行注记**：`#1069` 那条后面补「（该修复未在 4.7.0 生效，见 #1092）」。
   它已经发布过，但正文错着比注记错着更糟，且这是仓库自己记着的一笔账。
3. **`CONTEXT.md`**：§Release & upstream policy 里「group chat 未随行的 3.x 功能」改为 4.6.0 起已回来。
4. **`docs/rebase-v1.3.6.md:140`**：group-chat unit 行补上 `#1069`，与
   `docs/rebase-runbook.md:818` 的 family 表一致——这是目标书 §7 的第三条。

本轮自身的改动**不**写进 unit 表。

## 2. 代价

- 下一次 rebase 时，按 runbook 会重放 `#1069`：它的 8 个 lib 文件正好是本轮改过的
  `side_drawer.dart` / `home_page_controller.dart` / `home_page.dart` / 两种布局 / 群背景。
  重放会把一条**已被取代的参数链**加回管道，冲突只能靠当时现场判断。
- 届时没有人知道「本轮的实现就是 #1069 想做的事的另一半」——除了 commit message。
- 好的方面：文档改动最小，本轮不依赖「提交 sha」这类还没发生的信息。

## 3. 适合

认为 unit 表是**历史事实**（哪次提交重放了什么），不该混入「未来的改动打算怎么重放」。
