机制：工具处理器就是 await 子轮次，父回合停在 _executeClientTool；下一轮 HTTP 要等工具返回才发（tool_loop_runner.dart:128-140）。

协议层是安全的：等待期间没有挂起的连接；补发的请求是整段历史重放（request_history_context.dart:274 已去掉 previous_response_id），客户端也没有 idle 上限（dio_http_client.dart:107）。慢的是人眼，不是线。

排队而不是禁用：忙碌时输入进 _queuedInputs，这一轮结束后才发（home_view_model.dart:995）；忙碌是按会话算的，切到别的会话照常能聊。

这一版定下的

  • 一个工具、一个词、一次语义：delegate 返回时，子代理已经跑完。
  • 父模型的答复带着结果——用户问「查一下再修掉」时，看到的就是一句完整的话，而不是「已经派了」。
  • 父会话 Stop 级联取消子轮次，两处都干净收尾；父侧工具结果写 cancelled，父模型可以接着说。
  • 不需要「完成后通知」这套新机制，也就没有「父模型要不要为通知再醒一次」这个没人按按钮的计费问题。

必须接受的代价

  • 父会话从头占到尾。任务跑 5 分钟，这个会话 5 分钟内回不了第二句话；用户要么排队，要么换会话。
  • Stop 一刀两断。「算了别改了」和「停掉整个任务」共用一个按钮，想换话题就顺手杀了正在干的活。
  • 以后要做异步，工具面得改第二次。v3 的 ADR-0056 已经否决「一个工具 + wait 布尔」，所以升级不是加个参数，而是第二个工具。
  • 用户看不见进展。只有一个转圈和秒数；子代理是在读代码还是在跑测试，父会话里看不出来。（建议：卡片补一行子代理当前活动 —— 下一轮再定，不算已决。）

分水岭

A 是父模型替用户等。好处是结果落在一句话里、可回看、可复制；代价是这几分钟里那个会话不属于用户。

两个变体共用：同一个工具名 delegate、继承父会话的助手与工作区、深度上限默认 1、子会话禁用 ask_user 与审批类工具、幂等键 = 父会话 + 消息 + toolCallId、中断由渲染层派生而不落库。这个变体唯一要你定的：父会话是等，还是不等。
