# A — 两层：全局默认 + 助手覆盖

内置生图工具，不是本地工具开关：它始终在工具列表里，用的是「解析出来的绘图模型」。解析两层：

```
effectiveImageModel(assistant) =
    assistant.imageModel          // 该助手显式选的
 ?? global.imageModel             // 设置 → 默认模型 → 绘图模型
```

- **全局默认**（设置 → 默认模型 → 绘图模型）：所有助手、所有对话的兜底。这一页已经有 6 个辅助模型（标题、摘要、建议、压缩、翻译、OCR），绘图是第 7 个，形状完全一样。
- **助手覆盖**（助手编辑页 → 绘图 → 绘图模型）：一个助手想固定画风/成本时选一次，之后它的所有对话都用它。未选就显示「跟随默认模型（gpt-image-1）」，写明当前实际值。
- **对话层不设覆盖**：对话已经指向一个助手，要换就换助手；再叠一层只会让「这张图是哪个模型画的」更难回答。

## 工具是本地工具，默认关闭

- 绘图进助手的**本地工具**清单，和 时间 / 剪贴板 / 浏览器 同级；默认关，关了就不进模型上下文（朴素上下文优先）。
- 打开后工具始终注册；没配绘图模型时不隐藏，而是返回可执行的错误：`未配置绘图模型，去 设置 → 默认模型 → 绘图模型`。
- 绘图那一行的副标题直接写当前模型（`gpt-image-1`），省一次点进设置确认。
- 面板里的「模型」一行显示解析结果 —— 覆盖生效时，用户在这里看到实际绘图模型。

## 委托（subagent）：认同"高端模型委托低端模型"是主流

这是最常见的用法：贵模型做规划，把重复劳动丢给便宜的模型。它恰好说明**绘图模型不能跟着文本模型走** —— 委托降的是"写字的人"，不是"画笔"。

委托有两种形态，绘图模型的答案必须是同一个：

1. **模型降级委托**（主流）：父模型把子任务交给一个更便宜的文字模型。子任务里如果调 `generate_image`，用的仍是**所属助手解析出来的那支画笔**（助手 → 全局），不是"便宜模型自带的绘图能力"—— 文字模型没有绘图能力，图永远由 app 的内置工具画。
2. **助手委托**：子助手带着自己的 模型 / 提示词 / 工具 / 绘图模型，解析结果就是它自己那两层。

一条规则覆盖两者：**绘图模型只跟"这条消息属于哪个助手"，不跟"当前是哪个文本模型"。**

- 降级委托 → 画笔不变，画风/成本不变，子任务和主对话的图看起来是一套。
- 助手委托 → 画笔由子助手决定，因为子助手是另一个 owner。
- 两个形态都不需要额外的"绘图模型传递参数"，也不需要三层解析。

反例（为什么不在委托包里单独指定绘图模型）：父模型要同时决定"用哪个文字模型"和"用哪个画笔"，就得在委托时把两者都写明；子任务里画出来的图与主对话不一致，用户还得回父对话去找原因。第一版不做。


## 代价

1. 想让"这一次对话"临时换个绘图模型，得换助手或改设置。
2. 助手编辑页多一段；每个新助手要多做一次选择（或依赖回落）。
3. 工具与后端要多读一层配置，测试覆盖"显式 / 回落"两条路径。
4. 面板里的「模型」必须显示解析结果，否则覆盖生效时用户看不出来。

## 以后再加一层是加，不是拆

对话级覆盖如果真被要，加在 `effectiveImageModel` 里就是第三条 `??`，已有配置不受影响；反过来，先做三层再砍成两层，是删用户已经用上的配置。
