谁贡献什么 —— 这一片真正要钉死的那张表

东西来自怎么落实
系统提示、模型、工具集、MCP、技能、记忆、温度/推理目标助手子会话的 assistantId 就是目标；整条既有管线从它解析，一样都不挑。不 cherry-pick：跟它聊天是什么样，派给它就是什么样。
工作区 workspace.id / cwd调用方会话和今天一样从父会话 extras 复制。assistant.defaultWorkspaceId 永远不参与——这是上一片写死的线。
提权策略 + 上限调用方助手委派那一刻复制（subagent.escalation / .cap），不变。目标不能给自己扩权。
深度父会话 + 1不变。目标自己的子代理设置（模型 / 提权 / 深度）不参与：它是子，深度 1 不能再派。
模型优先级先调用方，再目标调用方「子代理模型」设了就用它（那是用户对本助手所有子代理的明确选择）；没设（「继承本助手」）→ 跟目标助手自己的模型走 → 全局默认。现有解析链已经是这个顺序，只是把目标而不是调用方交给 sendScheduledMessage。
父会话的续写调用方助手SubagentEntry.assistant 仍然是调用方——回报回来的是父的助手在说话，不是目标。

若你更想让「目标的模型总是赢」，是一行的事——在评论里说。

数据

  • 子会话 extras：subagent.target 从 'general' 变成 'assistant'，再加 subagent.assistant_id = <id>——它被派给谁的出处，之后用户在子会话里换了助手也还在。两个键都是上一片预留的扩展点，schema 仍是 5。
  • SubagentEntry：assistant 不动（调用方），多一个 targetName 给面板。
  • 协调器在 begin 里解析一次目标，把 目标 交给 turnStarter(assistant: …)；enqueueResult(assistant: …) 继续拿调用方。
  • 幂等键、结果消息、分隔线、队列：一个都不变。

失败模式

什么坏了系统做什么
写了名单外的名字rejected: unknown_assistant。名单是请求时算的，改名或删除发生在请求与调用之间，或模型凭记忆写——模型改派 general 或告诉用户，不留空子会话。
两个助手同名这个名字不进名单；仍被写 → rejected: ambiguous_assistant。用户给其中一个改名就好。
写了调用方自己的名字当作没写（general）。它就是默认值，拒绝没有意义。
目标在子代理跑的时候被删子会话按既有规则解析助手（resolveConversationAssistant 的回落），不中断。任何会话的助手被删都是这条路。
目标的模型 / provider 没了既有的 turn_not_started：子会话留空、条不出现、模型拿到拒绝。
目标一个工具都没开子代理就是没工具，和直接跟它聊一样。不替用户补工具。

代价

  • 名单按请求计费。开了委派的助手上，每个请求多 N 个名字。40 个助手就是 40 个名字。要收窄，以后在来源侧加一个「可指名」筛选——不是现在。
  • 模型只凭名字选。「助手 2」这种名字派不出有意义的目标，它只能派 general。
  • 助手一多，模型可能选错人。选错的代价是一次失败的委派，不是数据损坏：工作区不变、授权不扩、结果照样回来。

这一轮只定一件事：谁能被指名——任何助手（本方案），还是只有标了「可被委派」并写了一句介绍的助手（方案 B）。定了之后不动 UI 轮：表里的规则直接进实现与测试，界面上的两处改动在实现完一并过目。
