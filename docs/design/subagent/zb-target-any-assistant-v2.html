目标是一个显式的 id：general 或 assistant:<id>

delegate 多一个参数 target，模型每次都说清楚谁去跑：general 是本助手的分身，assistant:<id> 以那个助手的身份跑——系统提示、模型、工具集都是它的。这个值原样写进子会话的 subagent.target，不翻译、不加第二个键。工作区、授权、深度仍然只来自调用方。模型凭「名字 + 描述」认人，所以给助手一个通用的 description。

相对 v1 改了什么

  • 目标不再是「省略 = general」，而是枚举里显式的一项。只有一个助手时参数整个不出现，和今天一模一样。
  • 枚举值是 id 不是名字。名字会重、会改；id 不会。于是「两个助手同名」这个失败态整个消失，也不需要新的按名查找。
  • extras 只写一个键：subagent.target = 'general' | 'assistant:<id>'。上一片留的占位终于有了第二个值。
  • 模型解析留了接缝：函数签名已经带上 target，今天两种目标同一答案。
  • 新增 Assistant.description：通用、可选、默认空，委派名单和群聊导演两处读。

谁贡献什么 —— 这一片真正要钉死的那张表

东西来自怎么落实
系统提示、模型、工具集、MCP、技能、记忆、温度/推理目标助手子会话的 assistantId 就是目标；整条既有管线从它解析，一样都不挑。
工作区 workspace.id / cwd调用方会话和今天一样从父会话 extras 复制。assistant.defaultWorkspaceId 永远不参与。
提权策略 + 上限调用方助手委派那一刻复制，不变。目标不能给自己扩权。
深度父会话 + 1不变。目标自己的子代理设置不参与。
模型优先级先调用方，再目标接缝在这里：解析是一个纯函数 resolveSubagentModel(delegator, target)，签名已经带上 target。今天两种目标同一答案——调用方「子代理模型」设了就用它；没设 → 目标自己的模型 → 全局默认。测试按 kind 各钉一格（general / assistant）。以后要让它们独立（general 跟调用方的便宜模型、指名的跟目标走），只改这个函数和它的测试，调用方一处不动。
父会话的续写调用方助手SubagentEntry.assistant 仍然是调用方——回报回来的是父的助手在说话。

数据：一个词表，一处解析

  • subagent.target 终于有了第二个值：'general' | 'assistant:<id>'。模型发什么就落什么，读的人永远不用把两个键拼起来。schema 仍是 5。
  • 一个 choke point：这个词表只有一个 parse / encode，工具参数和 extras 共用——两个写者、一个读者，不许各写一份 startsWith('assistant:')。
  • Assistant.description：String，默认空，JSON 同级字段，走 copyWith / update 的既有管线。
  • SubagentEntry：assistant 不动（调用方），多一个 targetName 给面板——begin 时按 id 解析一次。
  • 幂等键、结果消息、分隔线、队列：一个都不变。

description 为什么比名字好、又为什么不是方案 B

  • 为什么需要：枚举是 id 之后，「名字：描述」是模型唯一的判断依据。没有描述，id 选择就只剩名字——「助手 2」派不出有意义的目标。
  • 为什么不是 B：B 是为一个功能配「开关 + 一句话」，没开就不存在。这是通用的「这个助手能做什么」，写一次，哪里需要模型认人就哪里读；没有「可被委派」这个概念，任何助手照样能被指名。
  • 第二个读者（已核实）：群聊导演今天给模型的每个成员只有 id + name——chat 导演的 roster（group_director.dart:205-212）和决策模型的 state（:359-362）。各加一行 'description'，非空才加：老用户的请求字节不变。
  • 边界：这一片只这两处读它。侧边栏、助手选择器、子会话标题栏都不显示。
  • 落地：字段 + 委派名单一个提交；导演读它一个提交（group_director_decision_test.dart 加一格「有描述的成员带描述、没有的不带键」），可单独撤。
  • 隐私：描述和名字一样是写给模型看的；系统提示永远不进名单。

失败模式

什么坏了系统做什么
写了名单外的 targetrejected: unknown_target。名单是请求时算的，删除发生在请求与调用之间，或模型写错了 id——模型改派 general 或告诉用户，不留空子会话。
写了调用方自己的 id当作 general。它就是默认值，拒绝没有意义。
目标在子代理跑的时候被删子会话按既有规则解析助手（resolveConversationAssistant 的回落），不中断；卡片上的名字查不到就回到今天的卡片。
目标的模型 / provider 没了既有的 turn_not_started：子会话留空、条不出现、模型拿到拒绝。
目标一个工具都没开子代理就是没工具，和直接跟它聊一样。
描述空着名单里只有名字——和没有这个字段一样。

删掉的一行：「两个助手同名」。id 唯一，这个失败态不存在了。

代价

  • id 比名字贵。一个 UUID 约 15 个 token，名单里出现两次（枚举 + 列表）：5 个助手约 250 token，40 个约 2000。要收窄，以后在来源侧加一个「可指名」筛选——不是现在。
  • 模型要照抄 id。抄错 → unknown_target → 重派。导演按 id 选人已经跑通（OpenRouter 端到端），这是同一种用法。
  • Assistant 多一个字段的 copyWith / JSON / update 管线，编辑页多一个输入框。
  • 助手一多，模型可能选错人。选错的代价是一次失败的委派，不是数据损坏。
