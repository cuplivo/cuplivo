发消息…

模型拿到什么：{status:"pending", job_id, placeholder_id}，文字继续流；默认 visible_to_you:false，不许假装看到了图。

用户在等什么：占位卡在调用位置，比例固定，图到了原地替换；失败/取消留卡可重试。

要图当答案时：模型另调 await_image(job_id) —— 阻塞留在那个工具里，不在默认路径上。

没变化的部分：schema 仍为 5，不建 job 表；job 只活在消息/tool call 的 metadata 里。

这一版定下的

  • 工具是非阻塞的：返回 pending，回复节奏不被打断；需要结果时再显式 await。
  • 占位卡属于这次调用，不新开一条图片消息；完成后原地替换。
  • 模型默认不检查图；结果里写明它看不见，避免编造。
  • 每会话并发 2，超限拒绝并提示；重启后未完成 → interrupted，不自动续跑。

必须接受的代价

  • 没批准就花钱：模型判断失误的一次调用照样计费，重试是第二次花钱。
  • 用户不能先改 prompt，只能取消；prompt 由模型写，可能跑偏。
  • 模型可能已经写「图在下面」，而图最终失败 —— 只能靠失败卡兜底。
  • 要让模型真的会调，得写工具描述、调提示词；不做就永远是摆设。

分水岭

A 是模型按下「开始画」。好处是零点击、不打断；代价是钱在用户看见之前就花出去了。

两个方案共用的部分：job 生命周期（queued → running → completed / failed / cancelled / interrupted）、原位置换、失败与取消可重试、重启中断、schema 5、先接一个后端。还没定的：工具命名与 await_image 的具体形态、默认后端、图像模型放全局还是按助手、占位卡的具体视觉、VLM 检查、context injection —— 都排在这一轮之后。
