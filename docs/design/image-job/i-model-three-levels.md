# B — 三层：全局 + 助手 + 对话

内置生图工具，模型解析三层，越靠内越优先：

```
effectiveImageModel(conversation) =
    conversation.imageModel                        // 这一条对话临时选的
 ?? assistant(conversation).imageModel              // 这个助手固定的
 ?? global.imageModel                              // 设置里的兜底
```

- **全局默认**：设置 → 默认模型 → 绘图模型，和另外 6 个辅助模型并排。
- **助手覆盖**：助手编辑页一段「绘图」，未选显示「跟随默认模型（当前值）」。
- **对话覆盖**：对话设置里一处「绘图模型」，未选显示「跟随助手（当前值）」。专门解决"这一次想用便宜模型多画几张"。
- 三处都显示**当前实际值**，否则用户无法回答"这张图到底是谁画的"。

## 工具是内置的

- 不占本地工具开关；始终注册。
- 没配任何绘图模型时返回可执行的错误，不隐藏工具。
- 面板里的「模型」一行显示最终解析结果（第三层的值）—— 这是唯一一处能一眼确认的地方。

## 委托（subagent）怎么继承

三层解析下，委托单位必须先钉死：

- **委托助手**：子助手带自己的 模型 / 提示词 / 工具 / 绘图模型，`effectiveImageModel(子助手)` = 它自己的三层（它没有对话时就是助手那一层）。父助手和子助手可以各画各的。
- **委托裸模型**：没有助手配置，只能继承调用方当时的解析值；再用对话层覆盖就说不清"这条对话"指哪一条（子任务通常没有独立会话 UI）。

两条都要写，才会出现"子任务画风突然变了而没人解释"的情况。所以 B 实际上要求：委托必须是助手，或者对话层在委托内部不可见 —— 这是一条隐藏规则。

## 代价

1. 三层解释成本高：同一个助手，不同对话可能出不同画风的图，用户找不到原因。
2. 助手编辑页 + 对话设置各多一段，第一版的设置面明显变大。
3. 工具/后端要多读两层，测试要覆盖 2³ 的组合里至少 4 条路径。
4. "临时换模型"的需求不一定要用对话层解决：换助手已经是一个现成的动作，而且意图更明确。

## 一个反例

对话层最诱人的场景是"这次用便宜模型"。但真正发生的频率通常低于"我一直用这个助手、这次想换画风" —— 后者其实是助手层的事。为低频场景先建一层，会让高频路径（"为什么这张图不一样"）变难回答。
