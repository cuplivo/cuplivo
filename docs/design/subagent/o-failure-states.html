四种：完成（勾）/ 失败（感叹）/ 取消（叉）/ 中断（断线）。只有失败那条用红，其余保持中性灰——取消和中断不是错误，是用户或系统让它停的。

为什么失败用红、取消不用

红色是「事情没做成」的信号；用户按了 Stop 不该被红字追责。中断同理——进程被杀是环境的事，不是这个任务的错。

点开去哪里：四种都进面板那一条；子会话里有完整的现场（失败原因在它自己的时间线上，那里本来就显示错误）。

失败的分隔线不带原因。一行 12.5px 塞不下「HTTP 502 upstream timeout」，而且原因要跟着改动文件一起读才明白——那属于子会话。

「已中断」在重启之后出现——它不是猜的：启动清理已经把那条 run 落成 interrupted（errorCode = app_restart）。

取消 / 中断之后能不能再来一次

v1 不给重试按钮。失败、取消、中断都只留现场：点进子会话看它做到哪，然后在父对话里再说一句——`delegate` 是模型的决定，重试也该是它的决定，不是一个卡上的按钮。

这也避免了一个坑：卡上的「重试」要处理「重试用的是哪个模型、哪个工作区、算不算同一个 job」——那套问题在 v3 里已经养过一次。

④ 要你定的那一件：失败要不要唤醒

A · 失败也唤醒（推荐）：分隔线之后，主代理说一句

「派出去改文案的那个回来了，没做成：上游 502，重试两次都超时。要我换个思路自己改吗？」——用户不用点任何东西就知道发生了什么，并且能直接回答。

代价：每次失败也多一轮生成；而且主代理可能把「失败」说得像「部分成功」——工具描述里得写死「失败就直说失败，别替它圆场」。

B · 不唤醒：只有一行「子代理失败 · 改登录页文案」

省一轮钱，也不打扰。但用户如果没注意那条线，就会以为事情还在做——这和你第 7 轮纠正过的问题是同一个。

这一版定下的（其余四项）

  • 条只留「需要你」的状态；失败 / 取消 / 中断一律从条上消失。
  • 分隔线四种形态同一行：完成 / 失败 / 取消 / 中断，只换图标和动词；只有失败用红。
  • 面板动词在右，颜色只区分「要你动手」与「已结束」。
  • 不给重试按钮：重来是模型的决定，在父对话里再说一句就是。
  • 「已中断」读的是启动清理落下的 interrupted，不是「读不到就算中断」。

必须接受的代价

  • 失败原因藏在两级之下（分隔线 → 面板 → 子会话），急的人要连点两次。
  • 取消与失败在视觉上差别很小（一个红、一个灰），只看颜色分不出来。
  • 没有重试：用户得自己组织一句话让模型再派一次，而模型可能不派。
  • 若选 A，失败也会花一轮钱；若选 B，失败可能被读者划过去。

这一轮只定一件事：子代理失败时，要不要唤醒主代理在主对话里说一句（A，推荐），还是只留一行「子代理失败 · label」（B）。其余四项（条只留需要你的、四种分隔线、撤掉重试、「已中断」读落库事实）如果你没有异议，我就按这个实现。
